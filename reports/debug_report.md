## 2. Problem Statement

The Bob-DebugFlow repository contains a small but realistic Python FastAPI REST API that manages
users and items against a SQLite database. The application was submitted for a structured debugging
session with six intentional bugs seeded across four source files, covering a range of real-world
defect categories: incorrect HTTP semantics, missing input validation, a query-filter guard
omission, an unhandled exception path, a floating-point arithmetic error, and a database resource
leak.

The goal of this session was to demonstrate that IBM Bob 2.0 can act as a full debugging workflow
orchestrator: systematically understanding the codebase, detecting all failures, tracing root
causes, investigating in parallel using subagents, implementing minimal targeted fixes under
developer approval, verifying correctness, producing a structured code review, and generating
measurable before/after productivity metrics.

## 7. Root-Cause Analysis (Phase 3)

**Bug ID:** B1
**File:** app/routes/users.py
**Line:** 28
**Symptom:** POST /users/ returns HTTP 200
**Root Cause:** `@router.post("/", response_model=UserResponse)` has no `status_code` argument;
FastAPI defaults to 200 for all POST handlers when the argument is omitted.
**Correct Behaviour:** POST endpoints that create a resource must return 201 Created per HTTP
semantics (RFC 7231). Adding `status_code=201` to the decorator fixes this.
**Evidence:** test_create_user_returns_201 asserts status == 201, receives 200.

---

**Bug ID:** B2
**File:** app/models.py
**Line:** 61
**Symptom:** Email field accepts any string including "not-an-email" and "nodomain"; API returns
200/201 for clearly invalid email addresses instead of 422.
**Root Cause:** `email: str` in `UserCreate` uses Python's plain `str` type. Pydantic performs no
format validation on `str` fields. Any sequence of characters passes.
**Correct Behaviour:** Changing the type annotation to `email: EmailStr` causes Pydantic to invoke
its email-validator integration and return 422 Unprocessable Entity for non-email strings.
**Evidence:** test_create_user_rejects_invalid_email and test_create_user_rejects_missing_at_symbol
both assert 422, both receive 200.

---

**Bug ID:** B3
**File:** app/routes/items.py
**Line:** 89
**Symptom:** GET /items/?description= (empty string) returns an empty list even when items exist.
**Root Cause:** The filter guard is `if description is not None:`. An empty string `""` is not
None, so the guard passes and the ORM executes `WHERE description = ''`. No items have an empty
description string in the database, so the query returns zero rows silently.
**Correct Behaviour:** An empty or blank description parameter should be treated as "no filter".
Changing the guard to `if description is not None and description.strip():` bypasses the filter
when the value is blank.
**Evidence:** test_list_items_empty_description_param_returns_all creates two items then calls
GET /items/?description= and asserts len(items) >= 2; receives 0.

---

**Bug ID:** B4
**File:** app/routes/items.py
**Line:** 66-67
**Symptom:** GET /items/99999 raises an unhandled KeyError that propagates as a 500 Internal
Server Error instead of a 404 Not Found.
**Root Cause:** The handler builds a dict of all items (`{item.id: item for item in ...}`) then
accesses it with `all_items[item_id]`. When item_id is absent from the dict, Python raises
`KeyError: 99999`. FastAPI does not catch raw KeyErrors; they propagate as 500.
**Correct Behaviour:** Use `db.query(ItemORM).filter(ItemORM.id == item_id).first()` which returns
None for missing IDs, then raise `HTTPException(status_code=404)` explicitly.
**Evidence:** test_get_nonexistent_item_returns_404 asserts status == 404; receives a KeyError
exception propagated as a 500 with a full stack trace.

---

**Bug ID:** B5
**File:** app/utils.py
**Line:** 30
**Symptom:** Prices with two significant decimal digits are silently truncated to one. 19.99
becomes 19.9; 4.55 becomes 4.5.
**Root Cause:** `return int(value * 10) / 10` multiplies the value by 10 (should be 100),
truncates to int, then divides by 10 (should be 100). The effective operation is floor rounding
to 1 decimal place, not 2.
**Correct Behaviour:** `return round(value, 2)` uses Python's built-in rounding and correctly
preserves 2 decimal places.
**Evidence:** test_price_rounded_to_two_decimal_places asserts stored price approx 19.99;
receives 19.9. test_price_rounding_preserves_cents asserts approx 4.55; receives 4.5.

---

**Bug ID:** B6
**File:** app/database.py
**Line:** 51-53
**Symptom:** No direct test failure. Structural defect: database connections are not returned to
the pool when a route handler raises an exception.
**Root Cause:** The `get_db` generator uses `try: yield db / except Exception: raise`. The
`except` branch re-raises without calling `db.close()`. On the normal path (after yield), Python
generator cleanup closes the session. But when an exception is raised inside the route handler
(e.g. a KeyError, a validation error, or an HTTPException), execution jumps to the except block,
which re-raises without closing. The session is leaked.
**Correct Behaviour:** Replace the `try/except` with `try/finally: db.close()`. A finally block
executes unconditionally regardless of whether an exception was raised.
**Evidence:** Static code analysis; confirmed by both Phase 3 and Subagent B in Phase 4.

## 14. Remaining Limitations

1. **Stale comments in module docstrings:** Seven WARNING findings from CodeReview identify
   comments that still describe fixed bugs (database.py:10, utils.py:8, users.py:12, items.py:12).
   These do not affect runtime behaviour but should be removed in a follow-up cleanup.

2. **Stale inline comments:** users.py:36 still says "email is not validated"; items.py:40 still
   says "round_price() itself contains bug B5". Both are now incorrect.

3. **Response model type inconsistency:** UserResponse.email (models.py:67) uses plain str rather
   than EmailStr. As a response-only model this is not a security defect, but it introduces a
   minor inconsistency with the input model.

4. **Missing boundary test:** test_items.py does not test GET /items/0 (item_id=0). This is a
   pre-existing gap, not introduced by the fix.

5. **B6 has no automated test:** The database session resource leak (B6) is verified by static
   analysis only. A test that deliberately triggers an exception inside a route handler and
   verifies the session is properly closed would provide stronger coverage.

6. **Coverage gaps:** app/database.py is at 67% coverage (lines 41-45 not exercised by tests
   that hit the exception path through get_db). app/utils.py is at 75% (format_price_display
   not directly tested).
